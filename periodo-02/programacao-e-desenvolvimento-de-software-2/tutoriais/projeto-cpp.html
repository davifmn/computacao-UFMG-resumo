Um projeto C++ de verdade, do zero

Em PDS I tudo cabia num arquivo só. Em PDS II os trabalhos práticos têm várias classes, vários arquivos, testes e trabalho em grupo. Este tutorial monta, passo a passo, o projeto codigo/formas, e todo código mostrado aqui é carregado direto dos arquivos reais.

1. A estrutura de pastas

Não existe estrutura obrigatória, mas esta é a convenção mais comum e a que os corretores esperam encontrar:

formas/ ├── Makefile # como compilar tudo ├── include/ # cabeçalhos (.hpp): a INTERFACE das classes │ ├── forma.hpp │ ├── circulo.hpp │ ├── retangulo.hpp │ └── teste.hpp # mini-framework de testes ├── src/ # implementações (.cpp) │ ├── forma.cpp │ ├── circulo.cpp │ ├── retangulo.cpp │ └── main.cpp # só o main: fica FORA dos testes ├── tests/ │ └── teste_formas.cpp # outro main, que roda os testes └── build/ # gerado pelo make (.o, executáveis) — não vai para o git

2. Cabeçalho × implementação

O cabeçalho (.hpp) diz o que a classe oferece: é o "contrato" que os outros arquivos enxergam via #include. O arquivo de implementação (.cpp) diz como. Comece pela classe base abstrata:

  • #pragma once impede que o cabeçalho seja incluído duas vezes na mesma unidade de compilação. A forma clássica equivalente é o trio #ifndef FORMA_HPP / #define FORMA_HPP / #endif.
  • = 0 torna o método virtual puro e a classe abstrata: ninguém cria uma "Forma genérica".
  • O destrutor é virtual. Veja o motivo na visualização de polimorfismo.

Uma classe concreta declara o que sobrescreve e guarda seus dados como private:

Invariante de classe: uma propriedade que vale para todo objeto válido (aqui, raio_ > 0). O construtor a estabelece, lançando uma exceção se não conseguir, e os métodos a preservam. Por isso os dados são privados: ninguém de fora consegue quebrá-la.

  • explicit impede conversões implícitas estranhas como Circulo c = 3.0;.
  • const no fim do método promete não alterar o objeto, e só métodos const podem ser chamados em objetos const.
  • A lista de inicialização : raio_(raio) inicializa os membros antes do corpo do construtor.

3. Compilação separada

Cada .cpp é compilado sozinho num arquivo objeto (.o). Depois, o ligador (linker) junta os objetos num executável. Se você muda só circulo.cpp, só ele precisa ser recompilado.

g++ -std=c++17 -Wall -Iinclude -c src/circulo.cpp -o build/circulo.o   # compila (gera .o)
g++ build/forma.o build/circulo.o build/retangulo.o build/main.o -o build/programa   # liga

Decifrando erros: "undefined reference to Circulo::area()" é um erro do ligador: o método foi declarado mas nenhum .o o define (você esqueceu de implementar ou de incluir o .cpp na ligação). Já "'Circulo' was not declared" é erro do compilador: faltou um #include.

4. O Makefile, linha a linha

Digitar esses comandos à mão não escala. O make lê regras no formato alvo: dependências e só refaz um alvo se alguma dependência for mais nova que ele.

  • $@ é o alvo, $< a primeira dependência, $^ todas as dependências.
  • % é um curinga: a regra $(BUILD)/%.o: src/%.cpp vale para qualquer arquivo.
  • | $(BUILD) é uma dependência order-only: a pasta precisa existir, mas mudar a data dela não força recompilar.
  • -MMD -MP faz o compilador anotar quais .hpp cada .cpp inclui, e o -include no fim carrega essas anotações. Sem isso, mudar um cabeçalho não recompilaria quem depende dele.
  • Atenção: as linhas de comando precisam começar com TAB, não com espaços.
make          # compila o programa
make run      # compila (se precisar) e executa
make test     # compila e roda os testes
make clean    # apaga build/

5. Testes de unidade

Um teste de unidade verifica automaticamente um pedaço pequeno do código. Com testes, você pode refatorar sem medo: se algo quebrar, o make test avisa na hora.

O que testar: o caso normal, os casos-limite (zero, vazio, um elemento, valores iguais) e os casos de erro (a exceção é lançada?). A macro TESTE vem de teste.hpp, um mini-framework de 50 linhas escrito para este repositório. Em trabalhos maiores, use o doctest, que tem a mesma cara (TEST_CASE, CHECK, CHECK_THROWS_AS) e é só um arquivo .h.

TDD (desenvolvimento guiado por testes): 🔴 escreva um teste que falha → 🟢 escreva o mínimo de código para passar → 🔵 refatore. Repita. Parece mais lento, mas você termina com código testado e um design pensado do ponto de vista de quem usa a classe.

6. Memória sem sofrimento: RAII

RAII (Resource Acquisition Is Initialization): amarre cada recurso (memória, arquivo, lock) à vida de um objeto. O construtor adquire, o destrutor libera, e o C++ garante que o destrutor roda quando o objeto sai de escopo, mesmo se uma exceção for lançada.

Em vez deUse
new T[n] / delete[]std::vector<T>
T* p = new T; (dono único)std::unique_ptr<T> p = std::make_unique<T>();
vários donosstd::shared_ptr<T> (conta referências)
char*std::string

Regra do zero: se sua classe só usa membros RAII (vector, string, unique_ptr), você não precisa escrever destrutor, construtor de cópia nem atribuição. Regra dos três/cinco: se precisar escrever um deles (porque gerencia memória na mão), escreva todos. Veja codigo/vetor.cpp.

7. Depurando

# Compile com -g (símbolos de depuração) e, de preferência, com os sanitizers:
g++ -std=c++17 -g -fsanitize=address,undefined -Iinclude src/*.cpp -o programa
./programa            # acusa acessos fora do vetor, use-after-free, vazamentos...

# Depurador: pare no erro e inspecione as variáveis
gdb ./programa
(gdb) run             # executa até travar
(gdb) bt              # pilha de chamadas (backtrace)
(gdb) print raio_     # valor de uma variável
(gdb) break circulo.cpp:8   # ponto de parada

No macOS, use lldb no lugar do gdb (comandos parecidos). O AddressSanitizer (-fsanitize=address) encontra em segundos bugs de memória que levariam horas com cout.

8. Git para o trabalho em grupo

git init                          # uma vez
git add include/ src/ tests/ Makefile
git commit -m "Adiciona classe Circulo com testes"
git switch -c feature/retangulo   # trabalhe em um ramo separado
# ... edita, testa ...
git commit -am "Implementa Retangulo"
git switch main && git merge feature/retangulo
  • Crie um .gitignore com build/: arquivos gerados não vão para o repositório.
  • Commits pequenos, com mensagem no imperativo que diga o que e por quê.
  • Rode make test antes de cada commit. Melhor ainda: configure a integração contínua (como a deste repositório) para rodar sozinha.

9. Checklist do trabalho prático

  • ☐ make compila do zero, sem avisos com -Wall -Wextra
  • ☐ make test passa, e existe teste para os casos-limite e de erro
  • ☐ Cada classe tem uma responsabilidade clara e dados private
  • ☐ Nenhum new sem dono (prefira RAII); o AddressSanitizer não acusa nada
  • ☐ Métodos que não alteram o objeto são const; sobrescritas usam override
  • ☐ README explicando como compilar, executar e as decisões de projeto
