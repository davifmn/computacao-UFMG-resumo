Projeto de software: princípios, SOLID e padrões

Projetar é decidir como dividir um sistema em partes e como elas conversam. O objetivo é um só: que o sistema continue fácil de mudar. Os princípios dizem o que buscar; os padrões são soluções testadas para problemas recorrentes. Os exemplos são de uma loja virtual, e o código completo (com testes) está no fim da página.

Coesão, acoplamento e ocultação de informação

  • Coesão alta: cada classe ou módulo tem uma única responsabilidade bem definida. Uma classe Pedido que calcula frete, envia e-mail e gera nota fiscal tem coesão baixa.
  • Acoplamento baixo: as partes dependem pouco umas das outras, e de preferência de interfaces estáveis, não de detalhes. Acoplamento ruim é aquele em que uma mudança num módulo obriga a mudar outros.
  • Ocultação de informação (Parnas, 1972): cada módulo esconde uma decisão de projeto que pode mudar (formato de dados, algoritmo, fornecedor) atrás de uma interface. Atributos privados são a versão mínima disso.

Outros dois princípios frequentes: prefira composição a herança (herança acopla a subclasse aos detalhes da superclasse) e a lei de Demeter ("fale só com seus amigos": evite cadeias como pedido.cliente.endereco.cidade.nome).

Padrões de projeto

Os 23 padrões do livro da "Gangue dos Quatro" (Gamma, Helm, Johnson e Vlissides, 1994) são divididos em criacionais, estruturais e comportamentais. Mais que decorá-los, vale reconhecer o problema que cada um resolve:

Strategy (comportamental): uma família de algoritmos intercambiáveis atrás de uma interface. O pedido calcula o total sem saber qual frete está usando.
Observer (comportamental): quem muda de estado avisa uma lista de interessados, sem conhecê-los. Pagar o pedido notifica o estoque e o e-mail.
Adapter (estrutural): converte a interface de uma classe que você não controla (um gateway antigo, em centavos) para a que o seu código espera.
Decorator (estrutural): embrulha um objeto para acrescentar comportamento, com a mesma interface. FreteComSeguro(FreteNormal()), e decorators se empilham.
Factory (criacional): centraliza a criação, para o cliente não depender das classes concretas: cria_frete("expresso").
Singleton (criacional): uma única instância global. Use com cuidado: é estado global disfarçado e dificulta os testes.
class Frete(ABC):
    @abstractmethod
    def custo(self, peso_kg, distancia_km): ...

class FreteExpresso(Frete):
    def custo(self, peso_kg, distancia_km):
        return 2 * FreteNormal().custo(peso_kg, distancia_km) + 15

pedido = Pedido(frete=FreteExpresso())   # o pedido não sabe qual frete é
pedido.total(distancia_km=100)

Code smells e refatoração

Refatorar é mudar a estrutura do código sem mudar o comportamento, em passos pequenos e com os testes passando o tempo todo (Fowler). Os sinais de que é hora, os code smells:

  • Método longo e classe grande → extrair método / extrair classe.
  • Código duplicado → extrair e reutilizar.
  • Lista longa de parâmetros → introduzir um objeto parâmetro.
  • Inveja de recursos (um método que usa mais os dados de outra classe que os da sua) → mover método.
  • switch sobre tipos → substituir condicional por polimorfismo (é o caminho que leva ao Strategy).
  • Números mágicos, nomes ruins, comentários explicando código confuso → renomear, extrair constantes, simplificar.

Arquitetura

Acima das classes, a arquitetura organiza o sistema em grandes blocos: camadas (apresentação, negócio, dados), MVC (modelo, visão, controlador), cliente/servidor, microsserviços (serviços pequenos e independentes que conversam por rede, com implantação separada: mais autonomia para os times, mais complexidade operacional) e arquiteturas orientadas a eventos (filas e publish/subscribe, o Observer em escala de sistema).
