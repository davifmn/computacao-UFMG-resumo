Git por dentro: commits, ramos e HEAD

O Git não guarda "versões de arquivos": guarda um grafo de commits, e cada ramo é só um ponteiro para um commit. Digite comandos no terminal (ou rode um dos cenários passo a passo) e veja o grafo mudar. Entender isso é o que separa usar o Git de ter medo dele.

$ git
Comandos do cenário

O modelo

  • Commit: uma fotografia do projeto inteiro + autor + mensagem + o(s) pai(s). É identificado pelo hash SHA-1 do seu conteúdo, por isso é imutável: mudar qualquer coisa gera outro commit.
  • Ramo (branch): um arquivo de 41 bytes com o hash de um commit. Criar um ramo é instantâneo, e commit só move o ramo atual para o commit novo.
  • HEAD: aponta para o ramo atual (ou direto para um commit, no estado "HEAD destacado").

Integrando trabalho

  • Merge com avanço rápido: se o ramo atual é ancestral do outro, basta mover o ponteiro.
  • Merge de três vias: compara as duas pontas com a base (o ancestral comum mais recente) e cria um commit com dois pais. Conflitos aparecem quando os dois lados mudaram as mesmas linhas.
  • Rebase: reaplica os seus commits em cima do outro ramo, criando commits novos. O histórico fica linear, mas a regra de ouro é: nunca faça rebase de commits que já foram publicados, porque quem os baixou terá uma história diferente da sua.
  • reset move o ramo para trás (reescreve a história); revert cria um commit que desfaz outro (seguro em ramos compartilhados).

Fluxos de trabalho. No GitHub Flow, cada mudança vive num ramo curto, vira um pull request, passa por revisão de código e testes automáticos (integração contínua) e é integrada à main. O trunk-based development vai além: ramos de horas, integração várias vezes ao dia e feature flags para esconder o que ainda não está pronto.
